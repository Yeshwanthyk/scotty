# OpenClaw cloud topology vs Scotty

## Scope and evidence

This report compares two pinned source snapshots, not current branches or deployment behavior:

- **OpenClaw:** GitHub archive at commit [`1482bf19a763acc59470faf3425b3cf559018b2c`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/), locally read only from `/tmp/openclaw-provenance.8W7wWd/openclaw-openclaw-1482bf1/`.
- **Scotty:** commit [`709f04e3c8720021fe1073ce8ffd61cfa712ccb2`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/).

Evidence is labelled **docs/contract**, **implementation**, or **test-verified**. In this report, **test-verified means checked-in test coverage inspected, not tests executed or passing**. No tests, deployment, or production canary were run for this report.

## Executive finding

In this snapshot, **OpenClaw cloud agent** means a normal Gateway session whose coding execution is placed on a disposable or paired remote machine. The Gateway remains the control-plane owner of the conversation, model/provider credentials, placement record, and reconciled workspace. “Agent” has two meanings depending on execution mode:

- `worker-turn`: the OpenClaw worker and turn loop run on the cloud box; model inference and provider authentication remain Gateway-owned.
- `remote-exec`: the agent loop (Codex app-server) remains on the Gateway; command, filesystem, and HTTP execution run on the remote node.

OpenClaw therefore separates **session/control ownership** from **execution placement**. Its cloud-worker implementation is an explicit provider/lease/enrollment system with replay-safe allocation and cleanup.

Scotty’s current “cloud agent” is different: the supported path is a Cloudflare per-session Sandbox Durable Object backed by a Cloudflare Container running Pi/Codex. The Session DO owns lifecycle state; R2 owns immutable backups; the container is an execution host, not the authoritative session store. Scotty has a registered runner protocol and control plane, but the inspected implementation rejects runner-backed session creation until native Pi RPC transport is proven. That is an intentional lifecycle gate, not evidence that the runner path is production-ready.

## Provisioning, remote execution, and recovery

### OpenClaw: provider lease plus enrolled node

The provider contract makes placement capabilities explicit: supported execution modes, whether provisioning precedes installation, whether node enrollment is required, preparation targets, and an exact operation-bound cleanup handle. [`src/plugins/capability-provider.types.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/plugins/capability-provider.types.ts#L265-L310) **(implementation/contract)**.

Crabbox resolves a deterministic lease ID from the operation ID, allocates/inspects it, runs setup, optionally prepares a project and warm image, then enrolls the node and waits for its device identity. Enrollment starts heartbeats only after the device identity is obtained. [`extensions/crabbox/src/crabbox-worker-provider.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/extensions/crabbox/src/crabbox-worker-provider.ts#L318-L420), [`extensions/crabbox/src/crabbox-worker-provider.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/extensions/crabbox/src/crabbox-worker-provider.ts#L421-L591) **(implementation)**.

The same contract distinguishes cleanup-confirmed from cleanup-indeterminate failures and forbids replay from reallocating merely to discover a lease. [`src/plugins/capability-provider.types.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/plugins/capability-provider.types.ts#L189-L263) **(implementation/contract)**. Dispatch also refuses to redispatch a failed placement before the old placement is stopped/continued, preventing ambiguous duplicate provisioning. [`src/gateway/server-methods/sessions-dispatch.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/gateway/server-methods/sessions-dispatch.ts#L346-L380) **(implementation)**.

### Scotty: authoritative actor plus controlled runtime

Scotty has a stronger explicit authority/recovery model for the current Cloudflare path. Create arms a hard cap and records idempotency/correlation/nonce/attempt metadata before the execution request; execution is bound to `{ provider: "cloudflare", runtimeName: sessionId }`. [`worker/src/session/object.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/session/object.ts#L3391-L3455) **(implementation)**.

The backup lifecycle requires quiescing/stopping Pi, syncing, and confirming an owned immutable backup before resume. Focused tests cover exact backup identity, refusal to restore an unconfirmed/currently-unowned backup, native Codex thread resume, and preservation of authority after unknown provider outcomes. [`worker/test/session-actor/backup-lifecycle-sandbox.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/test/session-actor/backup-lifecycle-sandbox.test.ts#L186-L368), [`worker/test/session-actor/backup-lifecycle-sandbox.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/test/session-actor/backup-lifecycle-sandbox.test.ts#L474-L617) **(test-verified)**. Vaporization reaches Gone only after ordered cleanup and absence proof; an unknown provider outcome retains cleanup authority. [`worker/test/session-actor/vaporize.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/test/session-actor/vaporize.test.ts#L196-L279) **(test-verified)**.

The material gap is not basic persistence safety. It is **portable execution placement**: Scotty’s registered runner transport has control/admission/reconnect tests, but the inspected create boundary intentionally stops before using it. [`worker/src/runner/control.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/runner/control.ts#L4-L70), [`worker/src/runner/object.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/runner/object.ts#L41-L115), [`worker/test/runner/runner-transport.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/test/runner/runner-transport.test.ts#L196-L266) **(implementation/test-verified)**.

## Ranked transferable improvements

1. **Define a Scotty execution-placement capability contract before enabling runners.** Borrow OpenClaw’s explicit mode advertisement (`worker-turn` vs `remote-exec`), target/runtime identity, enrollment requirement, and readiness metadata. Keep the current runner creation rejection until native Pi RPC and lifecycle proof exist. This is an abstraction improvement, not a request to add a provider catalog. Evidence: OpenClaw provider contract above; Scotty’s provider schema and rejection [`worker/src/session/contracts.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/session/contracts.ts#L20-L35), [`worker/src/session/object.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/session/object.ts#L3370-L3381).
2. **Reuse operation-bound allocation and cleanup semantics for any future remote runner.** A fixed operation identity, exact cleanup handle, and distinct “cleanup confirmed” versus “indeterminate” state would fit Scotty’s existing unknown-outcome and vaporize invariants. Do not copy Crabbox’s machine provider without a real Scotty provider boundary. Evidence: OpenClaw cleanup contract; Scotty unknown-outcome tests [`worker/test/session-actor/reducer.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/test/session-actor/reducer.test.ts#L395-L560).
3. **Make runtime/enrollment proof explicit for remote runners.** OpenClaw pins runtime artifacts and binds the first device identity to the exact environment; Scotty already has runtime/bundle digests and readiness proofs in its actor model. Reuse that shape for runner admission, not for the managed Cloudflare Container path. Evidence: OpenClaw runtime/enrollment types [`src/plugins/capability-provider.types.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/plugins/capability-provider.types.ts#L132-L168); Scotty authority/runtime proof [`worker/src/session-actor/authority.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/worker/src/session-actor/authority.ts#L38-L66).
4. **Expose accepted checkpoint versus live remote workspace as separate states.** OpenClaw explicitly documents the last-reconciled loss window and requires explicit redispatch for unaccepted mid-turn results. Scotty’s immutable backup authority is stronger for session recovery; the OpenClaw distinction would still help if Scotty later supports a remote runner. Evidence: OpenClaw lifecycle [`docs/gateway/cloud-sessions.md`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/docs/gateway/cloud-sessions.md#L115-L121) and reconciliation implementation [`src/gateway/worker-environments/worker-turn-execution.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/gateway/worker-environments/worker-turn-execution.ts#L489-L545).
5. **Adopt explicit placement observability only when there is more than one real destination.** OpenClaw’s environment projections distinguish dual-mode support and persistent/disposable hosts, and dispatch reports unavailable/failed placement without silently retrying. Scotty can use this later for Cloudflare versus proven runners; today it should not advertise runner availability as session-create capability. Evidence: OpenClaw environment tests [`src/gateway/server-methods/environments.test.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/gateway/server-methods/environments.test.ts#L321-L428); Scotty provider reporting/create gate above.
6. **Keep the deployment-proof discipline.** OpenClaw’s own profile documentation warns that provider-readiness checks do not prove allocation, setup, enrollment, or cleanup. That is a useful verification rule for Scotty’s future runner canary, not a reason to import OpenClaw’s backend setup matrix. [OpenClaw docs](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/docs/gateway/cloud-workers.md#L83-L91); Scotty deployment topology/tests [`infra/test/cloudflare-stack.test.ts`](https://github.com/Yeshwanthyk/scotty/blob/709f04e3c8720021fe1073ce8ffd61cfa712ccb2/infra/test/cloudflare-stack.test.ts#L364-L417).

## Non-applicable differences

- **Crabbox/AWS/Hetzner/Daytona/Upstash/Kubernetes provider catalog:** not a Scotty gap. Scotty deliberately uses Alchemy’s Cloudflare model and managed Sandbox/Container bindings; adding a parallel backend reconciler would conflict with that boundary.
- **OpenClaw Gateway SQLite placement store:** OpenClaw persists placement records in its local Gateway state database. [`src/gateway/worker-environments/placement-store.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/gateway/worker-environments/placement-store.ts#L1-L10), [`src/gateway/worker-environments/placement-store.ts`](https://github.com/openclaw/openclaw/blob/1482bf19a763acc59470faf3425b3cf559018b2c/src/gateway/worker-environments/placement-store.ts#L139-L150). Scotty’s Durable Object authority plus R2 backup model is a different, intentional authority boundary; SQLite parity is not required.
- **Paired-node desktop, portals, and device capabilities:** these are OpenClaw node products, not evidence that Scotty’s current browser/Pi/Codex session surface lacks a feature. Only the future remote-runner subset is comparable.
- **OpenClaw sandbox backends:** Docker/Podman/SSH/OpenShell/Crabbox sandboxing is a separate tool-execution placement feature from OpenClaw cloud-worker session placement. It should not be conflated with Scotty’s official Cloudflare Sandbox host.
- **Ephemeral machine discard versus Scotty’s persistent session container:** this is a lifecycle choice. OpenClaw optimizes replacement around Gateway checkpoints; Scotty optimizes Codex/Pi continuity around Session DO authority and confirmed R2 backups. Neither establishes a defect in the other.

## Bottom line

OpenClaw provides a mature, provider-neutral **remote placement lifecycle**: dual execution modes, durable lease identity, enrolled node proof, cleanup ambiguity handling, reconciliation, and replacement. Scotty provides a more explicit **Cloudflare session authority and backup lifecycle**, while its remote runner path is intentionally fenced before native Pi transport and deployed lifecycle proof. The highest-value transferable work is the placement/lease/enrollment contract and its verification gates—not OpenClaw’s cloud-provider catalog or Gateway storage model.

# Kitesurf fit for Scotty agent-browser E2E

## Status

**Superseded by `docs/kitesurf-first-architecture.md`.** This report predates proof of native sessionless Kitesurf launch through Scotty's Worker binding and the Sandbox SDK portal bridge. Its capability comparison remains useful, but its recommendation to keep colocated `agent-browser` is no longer the selected architecture.

## Original decision

The original recommendation was to keep `agent-browser` with colocated Chromium for the first PNG proof and add pixel WebM later. Kitesurf was treated as canary-only until Scotty had a secure preview bridge and per-engine capability tests. Those missing prerequisites were subsequently designed and are now covered by the superseding architecture.

Kitesurf lowers Browser Run CPU and memory, but Cloudflare explicitly trades away pixel-perfect rendering and implements only a subset of CDP. It is intended for compatible, ephemeral agent tasks—not visual-fidelity testing, video/WebGL, or long authenticated sessions ([Cloudflare blog](https://blog.cloudflare.com/kitesurf/); [Kitesurf docs](https://developers.cloudflare.com/browser-run/kitesurf/)). Those trade-offs reinforce the colocation decision in `docs/agent-e2e-visual-testing-options.md:61-74`, while that earlier note still needs revision from Playwright/trace-first to the current `agent-browser`/PNG-first slice.

## Credentials, bindings, and CDP targeting

Cloudflare documents two different authority paths:

1. A Worker browser binding is an authenticated Browser Run endpoint; Worker code launches through `env.MYBROWSER`, so no REST API token is needed in the Sandbox container ([Workers binding](https://developers.cloudflare.com/browser-run/reference/wrangler/)).
2. Direct CDP uses the account-scoped WebSocket endpoint plus an `Authorization: Bearer <API_TOKEN>` header, and Kitesurf is selected with `browser=kitesurf` ([CDP](https://developers.cloudflare.com/browser-run/cdp/); [Cloudflare blog](https://blog.cloudflare.com/kitesurf/)).

**`agent-browser` compatibility is conditional, not yet proved in Scotty.** Cloudflare says any CDP-compatible client can connect, so it can target Browser Run/Kitesurf only if it accepts a custom WebSocket endpoint and authorization headers. Current Scotty source cannot establish that client-side capability because Scotty does not ship `agent-browser`; make endpoint/header negotiation an explicit canary gate rather than assuming it.

Scotty currently has no browser binding: its runtime `Bindings` expose DOs, KV, R2, assets, and Worker secrets only (`worker/src/bindings.ts:6-22`), and Alchemy binds exactly those resources at `infra/cloudflare-stack.ts:167-189`. Its container agent environment contains the GitHub sentinel rather than a real GitHub credential and contains no Browser Run account/token (`worker/src/container-auth.ts:280-299`). Preserve that boundary.

There is also no existing `agent-browser` binary to retarget: current tests assert that neither `agent-browser` nor Chromium is in the checked-in toolset (`cli/test/cli.test.ts:2292-2310`), and the image's command probes omit both (`worker/container/Dockerfile:182-189`). A future direct `agent-browser`/CDP process in the container would need the remote WebSocket endpoint and authorization header, placing Browser Run authority in the container; that is the wrong shape. Instead, keep the planned bounded Scotty Pi tool (`worker/src/container-auth.ts:8-17`; `docs/agent-e2e-visual-testing-options.md:80-84`) and put any Browser Run adapter behind the Worker/DO. The agent should receive actions and artifact results, never a browser binding, account ID, CDP bearer token, or unrestricted endpoint.

A Worker-side adapter must also enforce Scotty's approved target/port policy. Moving navigation to Browser Run would otherwise move page egress outside the Sandbox controls that currently own process and port access (`worker/src/sandbox-runtime.ts:32-47,82-94`) and outside the local `127.0.0.1` transport (`worker/src/session.ts:299-303`).

## Architecture disposition

- **Replacement: reject.** It fails the live localhost path and weakens screenshot/video fidelity and lifecycle ownership.
- **Optional backend: defer.** Reconsider for securely reachable deployed/public targets. Use Browser Run Chromium when pixel and Playwright compatibility matter; expose Kitesurf only through an explicit capability profile with its own assertions and expected rendering differences.
- **Canary-only: choose now.** Once a synthetic target is publicly reachable without real credentials, run a small Kitesurf canary that proves CDP connection, JavaScript/DOM assertions, one screenshot, quota/error handling, and teardown. Do not make its pixels a release baseline, enable session recording, or put Browser Run credentials in the Sandbox.

**Net change to the vertical slice: none.** Kitesurf is a useful future cost/compatibility experiment, not a reason to add a preview bridge before Scotty has proven colocated `agent-browser` + Chromium, PNG capture, private artifact retrieval, and vaporize cleanup. This matches the existing Browser Run pivot condition in `docs/agent-e2e-visual-testing-options.md:200-209`.
